# Правила проверки кода

Сначала пользователь пишет код сам. По просьбе «проверь LLM-XX» Codex читает контракт и сохранённое решение, запускает открытые тесты, проверяет граничные случаи и проводит ревью. Не заполнять решение за пользователя и не показывать полный эталон без явной просьбы.

## Рубрика

| Критерий | Что проверяем |
| --- | --- |
| Корректность | Контракт, граничные случаи, валидация, отсутствие мутаций и численные ошибки |
| Дизайн | Простая декомпозиция, понятные имена, согласованные типы и отсутствие лишних зависимостей |
| Тесты | Свои обычные и граничные случаи, воспроизводимость, отсутствие подгонки под публичные примеры |
| Эффективность | Обоснованные время/память, отсутствие ненужных повторных проходов или сетевых вызовов |
| Объяснение | Почему решение работает, где границы применимости и как оно связано с LLM-сервисом |

## Формат обратной связи

1. Фактический статус запуска и число прошедших проверок. Если код не запускался — сказать это прямо.
2. Блокирующие ошибки со входом-контрпримером и ссылкой на строку/фрагмент.
3. Значимые улучшения, затем необязательные замечания по стилю; без переписывания всего кода.
4. Оценка рубрики: готово / нужны изменения / не проверено.
5. Один следующий шаг или подсказка. Полное решение выдавать только по явной просьбе.

Публичные тесты — конечный набор примеров, а не доказательство корректности на всех входах. Ревью LLM тоже может ошибаться. Статусы не означают коммерческий опыт. Новая версия кода требует нового запуска и нового ревью; хэш кода связывает результат с проверенной версией.
